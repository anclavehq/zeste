# zeste

**Headless** cookie-consent management for the web: it keeps the service catalog of
[tarteaucitron.js](https://github.com/AmauriC/tarteaucitron.js) (MIT) and replaces its engine and its UI.

| Package | Role |
|---|---|
| `@zeste/core` | Framework-free engine: state, cookie (tarteaucitron format), plugins (Google Consent Mode v2), tarteaucitron shim |
| `@zeste/services` | The tarteaucitron catalog split up: one module per service, synchronous metadata, code loaded on demand |
| `@zeste/svelte` | Svelte 5: reactive state (runes), `<ZesteProvider>`, `<ConsentGate>`, draft preferences, SSR |
| `@zeste/react` | React 18/19: `useZeste()` hook, `<ZesteProvider>`, `<ConsentGate>`, draft preferences, SSR (Next.js App Router) |
| `@zeste/vue` | Vue 3: reactive state, `v-model` on the preferences and the draft, `<ZesteProvider>`, `<ConsentGate>`, SSR (Nuxt) |
| `zeste` (CLI) | `npx zeste add`: banner, preferences and placeholder copied into your project, to edit. Ready-made for Bits UI, Ark UI, shadcn-svelte (Svelte), Radix, Ark UI, shadcn/ui (React) and Reka UI, Ark UI, shadcn-vue (Vue); with any other UI, start from one and swap the imports |
| `examples/vanilla` | Demo without a framework |
| `examples/sveltekit` | SvelteKit 3 demo (SSR, adapter-node) in plain HTML, no UI library |
| `examples/nextjs` | The same demo with Next.js 16 (App Router, SSR) |
| `examples/nuxt` | The same demo with Nuxt 4 (SSR) |
| `examples/svelte-spa`, `react-spa`, `vue-spa` | The same demo without a server framework (Vite, client-only); React 18 for the React one |
| `examples/skin-bits`, `skin-ark`, `skin-shadcn` | The same demos with Tailwind, using components generated by `zeste add` |
| `examples/skin-react-radix`, `skin-react-ark`, `skin-react-shadcn` | The same, with React and Next.js |
| `examples/skin-vue-reka`, `skin-vue-ark`, `skin-vue-shadcn` | The same, with Vue and Nuxt |
| `e2e` | Chromium tests (Playwright): the whole catalog with the network intercepted + real services on the real network |

```sh
pnpm install
pnpm test
pnpm --filter @zeste/services generate   # regenerates the catalog from tarteaucitronjs
pnpm --filter example-vanilla dev
pnpm --filter e2e test                   # browser tests (first time: pnpm --filter e2e exec playwright install chromium)
```

## Usage with SvelteKit

```ts
// +layout.server.ts — the choice is read on the server: no banner flash
export const load = ({ cookies }) => ({ consent: parseConsentCookie(cookies.get('tarteaucitron')) });
```

```svelte
<!-- +layout.svelte: one instance per request, never at module level -->
<script lang="ts">
  import { createZeste, ZesteProvider } from '@zeste/svelte';
  import { gtag, youtube } from '@zeste/services';
  import { messages } from '@zeste/services/i18n/fr'; // tarteaucitron texts, 36 languages
  let { data, children } = $props();
  const zeste = createZeste({ services: [gtag({ gtagUa: 'G-XXX' }), youtube()], initial: data.consent, messages });
</script>

<ZesteProvider {zeste}>
  {@render children()}
  {#if zeste.showBanner}
    <MyBanner text={zeste.messages.alertBigPrivacy} onaccept={zeste.acceptAll} ondeny={zeste.denyAll} />
  {/if}
</ZesteProvider>
```

```svelte
<ConsentGate service="youtube" embed={{ videoID: 'dQw4w9WgXcQ' }}>
  {#snippet placeholder({ service, allow })}
    <MyPlaceholder name={service.name} onclick={allow} />
  {/snippet}
</ConsentGate>
```

Without `messages`, the texts default to English. In a child component, `getZeste<Messages>()` (the `Messages` type
from `@zeste/services/i18n/types`) gives access to the typed texts: `zeste.messages.acceptAll`,
`zeste.messages.categories.analytic?.title`…

## Usage with Next.js (React)

```tsx
// app/layout.tsx (server component): the choice is read on the server, no banner flash
const consent = parseConsentCookie((await cookies()).get('tarteaucitron')?.value);
return <html><body><Consent initial={consent}>{children}</Consent></body></html>;
```

```tsx
// app/Consent.tsx
'use client';
export function Consent({ initial, children }) {
  // one instance per request on the server, one per page in the browser: never at module level
  const [zeste] = useState(() => createZeste({ services: [gtag({ gtagUa: 'G-XXX' }), youtube()], initial, messages }));
  return (
    <ZesteProvider zeste={zeste}>
      {children}
      <ConsentBanner>
        <p>{zeste.messages.alertBigPrivacy}</p>
        <Button {...zeste.actions.denyAll}>{zeste.messages.denyAll}</Button>
        <Button {...zeste.actions.acceptAll}>{zeste.messages.acceptAll}</Button>
      </ConsentBanner>
    </ZesteProvider>
  );
}
```

```tsx
<ConsentGate
  service="youtube"
  embed={{ videoID: 'dQw4w9WgXcQ' }}
  placeholder={({ service, allow }) => <MyPlaceholder name={service.name} onClick={allow} />}
/>
```

In a child component, `useZeste<Messages>()` returns the same object as in Svelte and re-renders on every change.
The differences: actions are props to spread (`{...zeste.actions.denyAll}`), the draft is edited with
`zeste.setDraft(key, checked)`, and a controlled dialog uses `open={zeste.preferencesOpen}
onOpenChange={zeste.setPreferencesOpen}`. With Next.js, add the zeste packages to `transpilePackages`
(they ship as TypeScript sources).

## Usage with Nuxt (Vue)

```vue
<!-- app/app.vue: useCookie reads the choice on the server too, no banner flash -->
<script setup lang="ts">
import { createZeste, parseConsentCookie, ZesteProvider, ConsentBanner } from '@zeste/vue';
const cookie = useCookie('tarteaucitron', { decode: (value) => value });
// one instance per request on the server, one per page in the browser: never at module level
const zeste = createZeste({ services: [gtag({ gtagUa: 'G-XXX' }), youtube()], initial: parseConsentCookie(cookie.value), messages });
</script>

<template>
  <ZesteProvider :zeste="zeste">
    <NuxtPage />
    <ConsentBanner>
      <p>{{ zeste.messages.alertBigPrivacy }}</p>
      <Button v-bind="zeste.actions.denyAll">{{ zeste.messages.denyAll }}</Button>
      <Button v-bind="zeste.actions.acceptAll">{{ zeste.messages.acceptAll }}</Button>
    </ConsentBanner>
  </ZesteProvider>
</template>
```

```vue
<ConsentGate service="youtube" :embed="{ videoID: 'dQw4w9WgXcQ' }">
  <template #placeholder="{ service, allow }"><MyPlaceholder :name="service.name" @click="allow" /></template>
</ConsentGate>
```

In a child component, `useZeste<Messages>()` returns the same object, reactive. Actions bind with
`v-bind="zeste.actions.denyAll"`, a dialog with `v-model:open="zeste.preferencesOpen"` and a switch with
`v-model="zeste.draft[key]"`. With Nuxt, add the zeste packages to `build.transpile`.

## With your UI library: `npx zeste add`

zeste is headless: it works with any UI, including your own components (see the end of this section).
`zeste add` is a shortcut that writes a first version with the libraries below, Tailwind classes included.

```sh
npx zeste add                  # detects the framework, then shadcn (components.json), Ark UI, Bits UI / Radix / Reka UI
npx zeste add --ui ark         # or explicitly: bits | ark | shadcn (Svelte), radix | ark | shadcn (React), reka | ark | shadcn (Vue)
npx zeste add --style pelure   # two styles: zeste (default, understated, lemon accent) | pelure (flat, thick outlines)
```

Colors live in `theme.css` (`--zeste-*` variables, scoped to the skin's elements): changing
`--zeste-ink` and `--zeste-accent` is often enough to match a site's colors. Dark mode via the `dark` class
or `data-theme="dark"`. The shadcn variants have no `theme.css`: they follow the project's theme. The shadcn/ui
(React) variant works with both of its flavors, Base UI (the default) and Radix.

This copies a banner, preferences and a placeholder into `src/lib/components/zeste/` (Svelte) or
`components/zeste/` in `src/`, Nuxt's `app/` or the project root (React, Vue), **written with your
library's components** (your shadcn components if there are any). Those files are yours: edit them freely,
`zeste add` never overwrites them without `--force`. The logic, the accessibility and the compliance checks stay
in `@zeste/svelte`, `@zeste/react` or `@zeste/vue` and are updated through npm.

With a custom design system, start from the closest variant and replace the imports: you only need to
attach the zeste actions to your own buttons.

```svelte
<ConsentBanner class="…">                       <!-- rendered only if the visitor has not chosen yet -->
  <MyButton {@attach zeste.actions.denyAll}>{t.denyAll}</MyButton>
  <MyButton {@attach zeste.actions.acceptAll}>{t.acceptAll}</MyButton>
</ConsentBanner>
<MyDialog bind:open={zeste.preferencesOpen}>
  <MySwitch bind:checked={zeste.draft.youtube} />
</MyDialog>
```

```tsx
<ConsentBanner className="…">
  <MyButton {...zeste.actions.denyAll}>{t.denyAll}</MyButton>
  <MyButton {...zeste.actions.acceptAll}>{t.acceptAll}</MyButton>
</ConsentBanner>
<MyDialog open={zeste.preferencesOpen} onOpenChange={zeste.setPreferencesOpen}>
  <MySwitch checked={zeste.draft.youtube} onCheckedChange={(on) => zeste.setDraft('youtube', on)} />
</MyDialog>
```

## Compliance guard (dev mode)

Consent rules across the EU (ePrivacy Directive art. 5(3), GDPR, and the EDPB guidance on cookie banners) boil down to
a few checkable points: refusing must be as easy as accepting, nothing non-essential runs before consent, and
withdrawing consent must stay possible at any time. Regulators such as the French CNIL enforce them actively.

The guard is on by default in development (`guard: true` to force it). It observes the **actual rendering**, whatever
the design system, and warns in the console if:

- the banner has no "Deny all" button at the first level, or it is invisible;
- "Deny all" is clearly smaller or less contrasted than "Accept all" (any CSS color, including Tailwind v4's `oklch`);
- nothing lets the visitor reopen the preferences once the choice is made.

It finds the buttons through `{@attach zeste.actions.*}`: a plain `onclick={zeste.denyAll}` works,
but is not checked by the guard.

## Tested guarantees

- **No request to a third party before consent**, verified at the Chromium network level for all 247 services.
  The "cookieless" modes of tarteaucitron that contact a third party before consent (Matomo Cloud, GetQuanty,
  advanced Consent Mode…) are disabled by default: opt in with `allowPreConsentRequests`.
- Every accepted service produces a real effect (script, iframe, pixel, tag queue).
- Exempt services (`needsConsent: false`, e.g. self-hosted Matomo) are loaded straight away.
- SvelteKit: banner and placeholders are present in the server HTML; a visitor who has already decided never sees the
  banner (not even for a frame); preferences have no pre-checked box; mounting a new embed does not reload the others;
  client-side navigation; consent withdrawal.
- Bits UI, Ark UI and shadcn-svelte skins: the same tests for all three (axe accessibility with no serious violation,
  keyboard, focus, switches announced as such, a guard with no false positive that detects a shrunken or low-contrast
  "reject" button — hex or oklch — or the lack of a link to change one's mind).
- On the real network (GA4, YouTube, Matomo Cloud): `_ga` cookies set only after acceptance and
  removed on withdrawal; YouTube iframe rendered / removed without a reload; Matomo hit sent; choice remembered.
